# Planner Multi-Step Fix — Report

Status: STARTED 2026-10-22 (coordinator, planner-fix)
Defect: on Vertex gemini-2.5-flash-lite, the agent planner degrades on multi-step work — step-budget exhaustion on clarification/artifact detours + LLM-call timeouts. Proven failures: re-run cases 1, 2, 5. Short paths work.

## Diagnosis
PROVEN (2026-10-22 ~11:21-11:30 PDT) by reproduction on an isolated stack (copy tree, gateway 8910 / engine 8911, Vertex gemini-2.5-flash-lite, fresh gcloud token) with the runtime's own audit trace (GET /api/agent/audit) captured per turn. Evidence: cases/diag/, cases/diag2/, ~/workspace/tmp-planner-fix/{diag,diag2}.log, probe-1 audit.

Observed traces:
- probe-1 ("What is the total revenue in the Sales sheet?", fresh thread, no answerer): plan#1 read_cells with a GUESSED range (0..1000 x 0..1000) -> FAILED "range too large: 1002001 cells (max 100000)"; plan#2 analyze_data ok (returns generic column MEANS, not the sum); plan#3 ASK (offer_options) "The total revenue ... is not directly available as a single sum from the previous analysis..." -> parked the full 240 s HITL wait -> "I didn't get an answer in time". Total 244.4 s — second-for-second the tour's case-2 turn-1 (244 s, no answer recorded).
- diag2 case-1 turn-1 (asks answered in ~1 s): analyze_data -> ASK "What columns contain the region information and the revenue figures?" -> analyze_data -> ASK "Would you like me to find the region with the highest total revenue...?" -> segments exhausted -> "I ran out of steps for that request." 9 tool calls, 2 asks, 10.6 s. The tour's case 1 took 75 s only because its answers were slower — the budget burn is structural, not latency.
- diag2 case-1 turn-2 + all later turns: HTTP 500 {"error":"agent error: openai-compatible backend: provider returned 429 (Resource exhausted...)"} — plan() throws propagate straight out of chat() (no containment) and kill the turn with the raw provider error. Same 500s in diag1. (429s aggravated by quota contention with the concurrent re-run; the failure MODE is the product gap.)

Mechanism (three linked parts + one robustness gap):
- M1 NO DIRECT PATH: for elementary data questions (totals, group-bys, filters) the flash-lite planner leads with analyze_data — whose lane answers with generic column means, the wrong statistic (same root cause as re-run case 3a) — or guesses an oversized read range that hard-fails at the 100k-cell cap, instead of reading the sheet's actual rows and composing the answer.
- M2 ASK-AS-FALLBACK + STATE DISCARD: when the analysis lacks the answer, the planner asks the user for facts the tools can obtain (which columns; "shall I find X?"). Each ask (a) parks the turn up to the 240 s HITL timeout when unanswered (AGENT_HITL_TIMEOUT_MS = 4 min in gateway agentSvc) -> the "didn't get an answer in time" terminations (tour cases 2/5; case 5's 278 s fits ask-answered + a 12-cell write crossing the confirmThreshold=10 approval gate and parking unanswered), and (b) when answered, runLoop RECURSES with toolResults=[] (runtime.ts ask branch) — all fetched data is discarded, so the next segment re-pays the full analyze/ask cost.
- M3 STEP BUDGET BURNED BY DETOURS: maxIterations defaults to 5 plan calls per runLoop segment (runtime.ts:242; the gateway passes no override). Analyze+ask cycles consume segments without progress; the planner keeps emitting tool plans (a plan with tool actions never ends the turn) and the budget dies -> "I ran out of steps" (tour case 1 both turns; diag2 reproduction).
- M4 NO CONTAINMENT FOR PLANNER-CALL FAILURES: backend.plan() throws (429 / 60 s per-call timeout in openaiBackend.ts:219 / invalid plan) propagate out of chat() — the route returns HTTP 500 with raw provider text. Under multi-step load (many plan calls per turn) transient provider errors are likely and each is fatal to the turn.
- Per-call latency is NOT the mechanism: on a quiet stack plan calls took ~1 s; the tour's slower turns reflect contention + the 240 s parks, not slow planning.
- NOT the mechanism: the scope gate (declines are instant + correct), the heuristic backend (the transcripts' questions are LLM-planner questions; the heuristic never asks them), the HITL machinery itself (asks answer correctly when answered — FIX-B proof + diag runs).

## Fix
LANDED in source (developed + validated in the isolated copy tree ~/workspace/icecream-sheets-pfx; identical files applied to ~/workspace/icecream-sheets at program end — real-repo dists NOT rebuilt, per the re-run guardrail):

1. M2 — packages/service/src/agent/runtime.ts, runLoop ask branch: the recursion after an answered ask now passes the accumulated `results` instead of `[]` (one-line change + comment). Fetched data survives asks; no re-read/re-analyze detours.
2. M3 — runtime.ts constructor: default maxIterations 5 -> 8 (commented). Legitimate read -> write -> verify -> compose chains get headroom; loops stay bounded.
3. M4 — runtime.ts runLoop: backend.plan() is wrapped — on a throw, log a 'timeout'-kind audit entry and retry ONCE after 1.5 s; on a second failure, end the turn with the graceful reply "The model service is busy right now, so I could not finish that request. Please try again in a moment." instead of an uncaught exception (HTTP 500 with raw provider text). PlannerInput/PlannerOutput added to the type imports.
4. M1 — packages/service/src/agent/openaiBackend.ts SYSTEM_PROMPT: new "DIRECT PATH FOR DATA QUESTIONS" block (bounded reads first — max 100,000 cells, start <=100 rows x 26 cols, never guess 0..1000x0..1000; compute from returned cells and finish with done; analyze_data is NOT for arithmetic/lookup questions; never ask for tool-obtainable facts; never "shall I...?"-confirm a requested analysis; reuse prior tool results after an ask). The ask bullet now reads: information readable via tools is never "missing" — read it instead of asking.

NOT changed (per brief guardrails): the two-source scope rule, the 2,000-char input cap, rate/concurrency guardrails, the MCP-only action rule, the §7 write-confirmation gate (case 5's approval park is intended behavior — the live proof answers it as a user would).
