### AREA 1 FINDINGS

#### F-1 CRITICAL — POST /auth/login mints a gateway JWT for ANY userId, with no production gate; deployed gateway is public
- Evidence: packages/gateway/src/gateway.ts:486 `if (path === '/auth/login' && method === 'POST')` — handler (L486-521) reads caller-supplied `userId` from the body and calls issueToken({userId, attrs:{tier}, secret: authSecret, ttlSeconds: loginTtlSeconds}) with NO credential check of any kind (only a per-IP rate limit). Comment at L488-493 admits "LOCAL-DEV ONLY... mints a signed JWT for ANY userId the caller names."
- No gate exists anywhere: packages/gateway/src/bin/gateway.ts:43-46 only warns when AUTH_SECRET is unset; grep for DISABLE/DEV_LOGIN/ALLOW_LOGIN across packages/ + deploy/ = no hits; createGateway registers the route unconditionally.
- Deployed posture makes it internet-reachable: deploy/services/gateway.yaml:32 `run.googleapis.com/ingress: all` (+ header L5 "public ingress — the gateway IS the auth point"); deploy/deploy.sh:338-339 grants allUsers run.invoker on the gateway; gateway.yaml L82-86 sets a REAL AUTH_SECRET from Secret Manager and L80-81 sets FIREBASE_PROJECT_ID — i.e. prod config is present, but nothing disables /auth/login.
- Exploit sketch: anyone on the internet, no credentials: `POST https://<gateway>/auth/login {"userId":"<victim Firebase uid>"}` -> valid 12h gateway JWT as that user -> full access to the victim's files/sessions via every /api/* route; userId "anyone" also works for a fresh full-access identity.
- Remediation (filed, not fixed — read-only audit): remove the route when FIREBASE_PROJECT_ID is set / behind an explicit ALLOW_DEV_LOGIN=1 env that deploy never sets; ideally delete from the shipped bin entirely.

#### F-2 CRITICAL (deploy config) — engines deploy in PROXY mode with a secret env name no code reads; engines are platform-public and trust a spoofable x-principal header
- Evidence: deploy/services/engine-standard.yaml env list (L57-74) sets ENGINE_SIGNING_SECRET (L71-74, from Secret Manager ${SECRET_ENGINE_SIGNING}) but NOT ENGINE_ACCESS_MODE and NOT ENGINE_ACCESS_SECRET; engine-xl.yaml:54-57 same pattern. Grep: the string ENGINE_SIGNING_SECRET appears NOWHERE in packages/ code — the code reads ENGINE_ACCESS_SECRET via engineAccessSecret() (packages/gateway/src/deploy/engineAccess.ts:67-70) and mode via engineAccessMode() (L62-64, default 'proxy'). packages/gateway/src/bin/engine.ts does not force signed mode.
- Consequence: engineSvc.ts:1447-1448 accessMode='proxy' -> the signed-mode gate (L3904) is inert; identity = principalOf(req) (L1999-2001) = requestPrincipal (packages/gateway/src/httpUtils.ts:82-86): raw `x-principal` header, default 'user'. Participant registration in proxy mode defaults callers to 'editor' (engineSvc.ts:3992-3994 comment + code).
- Exposure: deploy/deploy.sh:311-314 grants allUsers run.invoker on both engine services with the comment "engine validates the signed URL itself" — it does not, in this config; engine-standard.yaml:34 ingress: all.
- Exploit sketch: anyone on the internet: `curl https://<engine-standard-url>/execute -H 'x-principal: user:<victim>' ...` (or /load, /ops, /session/release) — no token at all -> full editor access to the live session that instance holds, as any principal they name.
- Same root cause on the gateway side: gateway.yaml sets neither ENGINE_ACCESS_MODE=signed nor ENGINE_ACCESS_SECRET, so POST /api/engine/access and /api/engine/open answer 501 (gateway.ts:716-723, L773-780) — the signed path is dead in the deployed config (fail-closed direction, but it means F-2's fix must wire BOTH sides: ENGINE_ACCESS_MODE=signed + ENGINE_ACCESS_SECRET (Secret Manager ${SECRET_ENGINE_SIGNING}) on engines AND gateway).
- Remediation (filed): rename/add env in engine yamls to ENGINE_ACCESS_MODE=signed + ENGINE_ACCESS_SECRET from ${SECRET_ENGINE_SIGNING}; add the same to gateway.yaml; until then restrict engine invoker to the gateway SA like the service package.

#### F-3 LOW — GET /auth/__audit is unauthenticated
- packages/gateway/src/gateway.ts:595-597: `if (path === '/auth/__audit' && method === 'GET') return reply('anonymous', 200, { ok: true, entries: [...audit] })` — no token check, sits before the /api auth pipeline. Leaks the last 500 requests' method/path/principal/status/timing to anyone. Info disclosure only; remove or auth-gate.

#### F-4 MEDIUM — MCP session routes: GET/DELETE unauthenticated; POST to an existing session not bound to its principal
- packages/mcp-server/src/http.ts:246-258: GET/DELETE with a known mcp-session-id go straight to transport.handleRequest — authPrincipal is never called (only a per-session rate limit). An unauthenticated DELETE terminates another user's MCP session; GET attaches to its server stream.
- packages/mcp-server/src/http.ts:201-220: POST with an existing sessionId calls authPrincipal (any valid token passes) but never compares the authenticated principal to the principal the session was created with (createServer defaultPrincipal, L232) — a second token holder who learns a session id can drive tools/call in the victim's session, executed as the victim's principal.
- Preconditions keep this Medium, not High: session ids are randomUUID (transport sessionIdGenerator L228) and unguessable; exploitation needs the id to leak (logs, shared infra). Still deviates from "401 on ALL routes" for GET/DELETE.
- Remediation (filed): run authPrincipal on GET/DELETE too, and store the creating principal on the SessionEntry and reject mismatches on all methods.

## AREA 3 — Session/Registry — verdict: FINDINGS (1 High, 1 Medium, 1 Medium; local-adapter + fail-closed PASS)

### (a) Claim CAS + epoch fencing
- Local adapter PASS: packages/gateway/src/deploy/fileRegistry.ts LocalFileRegistry.claim L282-297 runs inside a cross-process lockfile mutex (acquireLock L205-236, wx-create + stale recovery), checks stored epoch === expectedEpoch (null = no record) and new epoch === expected+1, atomic tmp+rename write. Exactly one concurrent claimant wins. Memory adapter L368-378 same semantics in-process.
- Heartbeat/release fencing PASS (all adapters): heartbeat L299-320 / L475-494 and release L322-335 / L496-510 return false unless stored sessionId AND ownershipEpoch match the caller — a stale owner cannot refresh or clear a lease it lost. Engine side enforces the consequence: engineSvc.ts ownership heartbeat L1769-1811 fences the session on epoch change, owner-instance change, heartbeat rejection, or registry-unreachable (when an epoch is held); fenced sessions refuse ops/loads (L3983-3995); evictSession releases with the epoch check (L3070-3072).
- Timing note (Low/observation, by lease design): fencing is detected at the owner's heartbeat cadence (lease/3, default 10s of a 30s lease — fileRegistry.ts:146-158), not per-op, so a deposed owner can serve ops for up to ~one heartbeat interval before fencing itself. Inherent to the documented lease design; noted, not scored.

#### F-5 HIGH — Firestore registry claim is NOT a transaction: read -> set -> re-read race can crown two owners (prod adapter)
- Evidence: packages/gateway/src/deploy/fileRegistry.ts FirestoreFileRegistry.claim L456-473: `const cur = await this.lookup(...)` ... `await this.doc(...).set({...record...})` ... re-read and return whether the doc still shows MY sessionId+epoch. There is no transaction: the FirestoreLike surface it is built on exposes only get/set/delete (packages/gateway/src/deploy/sessionStore.ts:377-390 FirestoreDocLike/FirestoreLike — no runTransaction).
- Race: two simultaneous first-opens interleave A.lookup(null) / B.lookup(null) / A.set(epoch1) / A.re-read(sees A -> true) / B.set(epoch1, B's session) / B.re-read(sees B -> true). Both gateways believe they won, both engines hydrate the file -> exactly the split-brain (two sequencers, unmergeable revision orders) the registry exists to prevent. The class doc comment (L446-454) acknowledges "read-then-CAS" and leans on the epoch as a "fencing guard", but the epoch cannot fence here because both claims write the SAME epoch value (1, or N+1 on takeover of an expired lease — same race applies to takeovers).
- heartbeat (L475-494) and release (L496-510) have the same check-then-merge-write TOCTOU: a stale owner's in-flight heartbeat/release that read the record BEFORE a takeover can land its merge AFTER the winner's claim write, overwriting leaseExpiry (release sets leaseExpiry:0 on the NEW owner's record — killing its lease and inviting a third claim) and regressing currentRevision/storedRevision.
- Exploit sketch: two authenticated users (or one user double-clicking / two gateway replicas — gateway maxScale 20) open the same never-opened (or lease-expired) file at the same moment against the prod Firestore registry -> both get joined:false creator replies with editor tokens for two different engine sessions of the same file; edits diverge silently.
- Caveat: as deployed TODAY this adapter is dormant — gateway.yaml wires no FILE_REGISTRY_STORE/SESSION_STORE and createGateway's default createFileRegistry(process.env) (gateway.ts:325-336) gets no injected Firestore client, so prod mode would throw and 503 (fail-closed), and local mode uses the (correct) Local adapter — but on a single gateway container's ephemeral FS, which is its own multi-replica hazard (see F-7 note). F-5 fires the moment the Firestore adapter is wired as designed (createFileRegistry with firestoreDb).
- Remediation (filed): implement claim/heartbeat/release with a real Firestore runTransaction (extend FirestoreLike with a transaction primitive); until then do not wire the Firestore adapter.

### (b) Join handshake — connection-info only PASS; role authorization FINDING (F-6)
- Shape PASS: gateway.ts open handler returns only {fileId, sessionId, engineUrl, accessToken, role, revision, joined, ownershipEpoch} (openReply L847-865); token scope {sub, sid, fid, role} with TTL = engineAccess ttl (default 600s); engine validates the token itself on join/use (engineSvc.ts:3904-3953 above). Registry lookup failure -> 503 (L867-870); claim CAS throw -> 503 (catch at L966); CAS loss -> re-read + JOIN winner (L972-1000), never a competing copy.
#### F-6 MEDIUM — Join role is self-asserted by the joiner; no ACL/share check on joining a live session
- Evidence: gateway.ts:800 `const requestedRole = (b.role as EngineAccessRole | undefined) ?? 'editor'` — the role comes from the REQUEST BODY, validated only to be 'editor'|'viewer' (L796-798). On the JOIN path the gateway issues the token with that self-chosen role (openReply L885-893) and records it in participants via noteParticipant (L881-884). The only authorization on open is the catalog check (L812-828): if a userFileCatalog record exists, non-owner -> 404; with NO catalog record, "unchanged Phase 2 behavior" = any authenticated principal who knows the fileId joins, as editor if they ask.
- Downstream: the self-asserted role propagates — registry participants map feeds agentSessionResolver.roleForPrincipal (agentSessionResolver.ts:153-161), so a self-declared 'editor' joiner's AI agent also gets editor engine tokens (agentSvc.ts:156-165).
- Mitigants: fileIds are `file-<randomUUID()>` (gateway.ts:809) — unguessable; catalogued (uploaded/product) files are owner-only at open. Residual risk: any fileId that leaks (share flows, logs, a collaborator gone rogue) grants silent editor + agent-write access with no share record to revoke; a legitimate viewer-share recipient can re-open with role:'editor' and upgrade themselves.
- Remediation (filed): derive join role from an authoritative record (catalog/share store) server-side; never from the request body; default viewer when no grant exists.

### (c) FAIL-CLOSED when registry DB unreachable — PASS
- Gateway: lookup throw -> 503 'session registry unavailable' (gateway.ts:867-870); claim throw -> 503 (L969-971); registry construction failure (incl. prod-without-Firestore-client, createFileRegistry L538-549 throws) is remembered and open answers 503 with fileRegistry=null (gateway.ts:325-336, L781-783). No fall-through to a local copy anywhere in the open path.
- Engine: ownership heartbeat fences on registry-unreachable when it holds an epoch (engineSvc.ts:1777-1781); /session/claim registry-read failure falls through to a fresh pending session BUT the gateway's subsequent CAS claim is the arbiter and 503s if the registry is truly down (engineSvc.ts:4255-4261 + gateway.ts:966) — the pending session is never confirmed to a client. Acceptable.
- F-7 note (config, Low): as deployed (gateway.yaml env), the gateway registry defaults to LocalFileRegistry on the container's local FS (fileRegistryProvider: SESSION_STORE unset -> 'local', fileRegistry.ts:155-162). With gateway maxScale 20 (gateway.yaml:36) each replica arbitrates only its own opens. Dormant today because /api/engine/open 501s without engineAccess (F-2), but wiring signed mode without FILE_REGISTRY_STORE=prod + a transactional adapter (F-5) would silently break the one-owner invariant across replicas.

### (d) Release / checkpoint auth — FINDING (F-8)
- Registry-level release is epoch+session fenced (above) — a stale OWNER process cannot release a new owner's record.
#### F-8 MEDIUM — Engine POST /session/release has no creator/owner check: any session participant (incl. a viewer joiner, or any holder of a self-minted legacy token naming the sid) can evict the shared session for everyone
- Evidence: engineSvc.ts:4126-4147 — the handler checks only that body.sessionId === state.sessionId and the session is active, then evictSession(reason). It never checks principal against the session creator/owner or participants. In signed mode the global gate only proves the token names this sid (L3944-3948); /session/release is not in the fileScopedRoute set (L3959-3966), so even a legacy fid='' token works — and such a token is self-service: POST /api/engine/access (gateway.ts:716-757) mints one for ANY sessionId the authenticated caller names, role defaulting 'editor', fid ''. The CLIENT enforces creator-only release (apps/web/src/services/collabTransport.ts:1261-1264 "Only the creator releases — a joiner never tears down a session it does not own"; L1496-1500), but the server does not.
- Impact: availability/integrity-of-service, not data loss — evictSession checkpoints first (released session rehydrates with checksum), so a malicious/buggy joiner (viewer included) can repeatedly tear down the live session under all collaborators; each eviction forces full re-open/rehydrate and drops SSE subscribers (engineSvc closeAllSubscribers on evict path). Repeatable at will while they hold any sid-scoped token.
- No separate client-callable /session/checkpoint route exists in engineSvc.ts (checkpoints are internal: evict/autosave/library-save paths), so checkpoint auth reduces to the registry epoch fencing above — PASS.
- Remediation (filed): in /session/release require accessClaims.sub (or proxy principal) === the session's creator principal (state's recorded owner), or at minimum an editor participant; reject viewer tokens.
